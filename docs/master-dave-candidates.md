# Master DAVE: coding-agent candidates

Research date: 2026-11-10. Branch: `feat/master-dave`.

Status: proposal for review. No packages, servers, or skills have been installed or enabled; runtime configuration is unchanged. Presentation cleanup is still pending approval.

Confirmed direction from all 35 interview answers: an independent Pi-based personal agent that Sawyer will open-source, reusing selected ideas from the earlier Python dave-harness. Support existing project stacks, mainly Python, and cover fixes, incremental features, reviews, new projects, architecture, and initial implementation. Issue tracking and project status are in scope, with GitHub, Redmine, and GitHub Actions as the initial integrations. Target Linux terminal and VS Code first, keeping the design portable. Keep the core open source; paid or hosted services are optional and explicitly configured.

DAVE should own assigned tasks and delegate within their scope, with writing workers in separate Git worktrees and main-agent review of integration. Keep one active task per session and a visible follow-up queue; use pi-agent-hub for individual DAVE instances and subtask visibility. File edits, checks, and feature branches may proceed within a task; dependency installs, migrations, and commits require approval, alongside the existing deletion/sending/publishing rules and never-push preference. Completion requires acceptance criteria, relevant checks, diff review, and browser verification for UI changes, with skipped/unavailable checks reported. Keep generated tests minimal and meaningful, with test-first work preferred for fixes and risky behavior changes. Hand off a concise summary, evidence, reviewable diff, limitations, and relevant documentation updates.

Use project memory plus a small global preference store; explicitly display every addition and its level. Support configurable providers and models per role with explicit hosted/local profiles. Prefer local processing, storage, tools, inference, and embeddings wherever practical. Approved model providers may receive task-relevant code when needed; search and other external services should receive only public/general queries by default. The user can override the privacy policy as needed. This is a local-first design target, not a guarantee that all work stays offline.

Always maintain Guard and Judge with DAVE as a core architecture component. Require Guard–Judge to be the first hook for every tool or command invocation, harden enforcement, and improve rule configuration/modification UX. Evaluate deterministic rules on every invocation and call Judge for unknown or ambiguous actions. If Judge is unavailable or uncertain, keep rules enforced and require approval for unresolved actions; block those actions without an interactive user. Prove hook ordering and coverage across actual tool, shell, MCP, extension, Hub, and worker execution paths before claiming this requirement is met. Use Guard/Judge initially and add OS/container isolation for selected projects later. Grants and privacy overrides default to task/session scope, workers receive narrower grants, and persistent project rules require explicit selection.

Prefer a few focused custom extensions and reuse existing tools elsewhere. Follow repository conventions with shared DAVE defaults; inspect the repository to infer standards when project instructions are absent, labeling those standards as inferred. Clarify material uncertainties and write plans for substantial work. Categorize unrelated improvements and log tasks for later; evaluate Clef/System One as a classifier for that intake. Browser access defaults to local apps; signed-in sites require authorization and separate profiles. Persist task/plan/decision/question/worker records and revalidate on resume. Continue workers only when explicitly left running. Allow two transient-failure retries, change approach for persistent failures, and ask when unresolved; permission denials are not transient failures. Start with at most two workers and configurable time/token/spending caps.

Maintain a reviewed, pinned baseline. Add the proposed [`/dave-update` workflow](master-dave-update.md) to fetch, review, implement, and verify updates and automatically reuse or create a matching package-update PR against `thesawdawg/agent-dave`. For v2, periodically review the previous configurable `n` tool events with Judge to detect suspicious sequences that individual decisions missed.

These are design decisions; the research-only instruction still applies. The [interview record](master-dave-questions.md) is complete. Specific frameworks, representative repositories, providers, budgets, integration write permissions, compatible package versions, and other implementation parameters remain open; package selections below are still provisional.

## Selection approach

**Evaluate first** means a strong candidate for a small trial after review. **Conditional** means useful only if the corresponding workflow is wanted. **Alternative** means choose against another entry. **Defer** means the benefit appears too small for the baseline.

Use Pi extensions for session behavior, process control, UI, and enforcement; MCP servers for external systems or reusable tools; and skills for instructions and repeatable methods. A CLI plus a skill can be simpler than adding an MCP server for an existing local command.

Pi now includes MCP and Codemode. Native configuration already uses `.pi/mcp.json`. An extension registering `/mcp` can replace the built-in implementation; adding an adapter is an explicit transport choice, not a prerequisite. Start evaluation with native MCP. Sources: [Pi MCP documentation](https://pi.dev/docs/latest/mcp), [packages](https://pi.dev/docs/latest/packages), [skills](https://pi.dev/docs/latest/skills).
